# tyche Audit Report — 2026-11-04

**Scope:** a P(-1) hardening, optimization and repair sweep (first-party
standards, *P(-1): Hardening*) over the whole repository outside vendored
`lib/`: `src/`, `tests/`, `scripts/`, `dist/`, CI and release workflows, and
the documents. **Baseline:** 1.2.1 (commit `c3f0e2f`, cyrius 6.7.18).
**Result:** 1.2.2.

## Executive summary

One real defect. A zeroed `_rng_state` made `rng_normal` loop forever.
Consumers write that cell directly to restore checkpoints, as `docs/api.md`
documents, and 0 is xorshift's fixed point. From state 0, `rng_u64` returned 0
forever, `rng_uniform` returned 0.0 forever, and every polar point landed at
s = 2 and was rejected. `SECURITY.md` said no input could do this. 1.2.2 makes
state 0 step as state 1, the bump `rng_seed` already applies. Every nonzero
state steps exactly as before, so no stream reachable through the API changes.

The rest is hardening and speed:

- The release workflow pinned third-party actions by movable tag while holding
  `contents: write`.
- The CI gate inherited that write token when the release workflow called it.
- The lint gate still tolerated an obsolete warning class and skipped `tests/`.
- `rng_seed`'s bump branch was never exercised by any test.
- `rng_normal` is 4.1% faster and `rng_uniform` about 1 ns faster, both
  bit-identical.

Nothing else was found. tyche has no I/O, no parsing and no allocation, and the
not-a-CSPRNG boundary is intact.

## Method

- **Toolchain sweeps (6.7.18):** `cyrius audit` (fmt / lint / docs / tests /
  bench), `cyrius coverage` (4/4 public fns), `cyrius doc --check`,
  `cyrius deny`, `cyrius vet`, `cyrius lint --strict-deferrals` on `src/` and
  `tests/`, `cyrius deps --verify`. All clean before and after.
- **Manual review** of every non-vendored file, and a diff of the workflows
  against the cyrius 6.7.18 `cyrius init` templates.
- **Reproductions:** the zero-state hang (`rng_normal` from `_rng_state = 0`,
  killed after 5 s), and the aarch64 exit path (`syscall(60, 3)` exits 3 under
  qemu, so the aarch64 CI leg was a real gate).
- **Codegen inspection:** disassembly of a probe function, to see what an f64
  builtin costs (see *Observations*).
- **Mutation testing** of the new tests and fuzz checks (five mutants).
- **Stream identity:** the 512-line golden dump (unseeded stream, 10 edge seeds,
  a 1M-draw digest per entry point) is byte-identical between 1.2.1 and 1.2.2 on
  x86_64 and on aarch64. Also, 200,000 consecutive `rng_normal` draws (seed
  2026) match `scripts/kat_reference.py` on both targets.
- **Consumer toolchain:** a program built against the 1.2.2 `dist/tyche.cyr`
  compiles and matches the reference under cyrius 6.6.2 (six of the seven
  consumers' pin) and 6.7.18, on both targets.
- **Benchmarks:** `scripts/bench-history.sh` (new) before and after, in one
  session, median of three runs.

### Performance — bit-identical

| # | Change | Before → after (same session) |
|---|---|---|
| P1 | `rng_normal` draws each coordinate straight from `rng_u64()` as `m·2^-52 − 1`. `rng_uniform()` is `m·2^-53` exactly and doubling is exact, so the operand of the subtraction is the same bits. This saves one call level and one multiply per coordinate. | `rng_normal` 345 → 331 ns (−4.1%) |
| P2 | `rng_uniform` is one `return` expression marked `#inline`, so cyrius replays it at the call site. | `rng_uniform` 5.74 → 4.74 ns with and without `#inline` on the same tree; 7 → 5 ns against the 1.2.1 row |

Unchanged: `rng_seed` 6 ns and `_rng_ln` 281–282 ns. `rng_u64` is +0.3 ns,
from finding 1.

## Observations — not changed, and why

- **`_rng_ln` is bound by the compiler, not the source.** cyrius generates
  stack-machine code: each f64 builtin is about 11 instructions (push/pop
  through memory, GPR↔XMM moves, the SSE op), and the linear-scan allocator
  keeps locals in five callee-saved registers. At about 220 operations, that
  gives ≈1.3 ns each. No source rewrite of the same operations moves this
  meaningfully. A different algorithm would, but it is a stream change (see the
  roadmap).
- **The `tt_hi * 0` term in `_rng_ln`** keeps the general double-double product's
  operation sequence. Dropping it saves 2 of ~220 operations (~1%), but proving
  the bits unchanged needs a signed-zero argument plus a matching edit to the
  reference. That is not worth it in a patch release.
- **`rng_u64` cannot be `#inline`**: cyrius inlines only bodies of at most 32
  tokens with no `var` or branch. Rewriting it on the global directly exceeds
  32 tokens.
- **`_rng_ln` keeps a precondition rather than guards.** It is internal, and its
  one caller only ever passes s in [2^-104, 1). Out-of-domain inputs give
  meaningless results (ln 0 → ≈ −709), and guards would cost on the hot path.
- **The installer is fetched from cyrius `main`** (`curl … | sh`), the upstream
  template's form. Since 6.6.20 it refuses a release whose signature it cannot
  fetch. Pinning the installer to the toolchain tag would trade installer fixes
  for reproducibility, and the binaries come from the same repository anyway.
- **`cyrius init`'s `programs/smoke.cyr` was not adopted.** It assumes
  `src/main.cyr` is the library header; in tyche that file is the smoke demo,
  which CI already builds and runs.
- **xorshift64 is F2-linear** (unchanged since the 2026-09-25 audit): it is frozen
  and documented as statistical only.

## Stream impact of 1.2.2

None for any state the API can produce. `rng_seed` never yields 0, and from a
nonzero state xorshift never reaches 0, so only a 0 written into `_rng_state`
sees the new rule: it steps as state 1 (first draw `0x0000000040822041`)
instead of sticking at 0. A checkpoint captured from a running stream is never
0, so restoring one is unaffected.

## Downstream

The consumers' suites were not re-run. Their streams are unchanged by the
argument above, and the shipped bundle compiles under their oldest toolchain
pin (6.6.2) with the reference's bits. Their manifests were read on
2026-11-04: agnosai pins tyche 1.1.0, and the other six pin 1.0.1.
